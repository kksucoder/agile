## 1. 概述

### 1.1 文档目的

本文档将 PRD 中的功能需求转化为可执行的工程蓝图，回答四个问题：

1. **做什么**：MVP 的完整功能边界（15 项 P0 能力）与明确排除项；
2. **怎么拆**：每项能力拆解为可估时、可验收的用户故事（Story）与验收标准；
3. **怎么做**：总体技术方案（已定稿技术栈）、数据模型、API 规范、通知与代码证据采集、AI 证据链与智能更新专项设计；
4. **怎么管**：16 周里程碑计划、团队分工、质量门槛、风险与交付物清单。

> v2.0 相对 v1.0 的变化：第 2 章技术方案按两份调研文档定稿（前端 React 19 体系、后端 Spring Boot 4.1.1 + Java 21 + MyBatis-Plus 3.5.17）；功能故事、数据模型、里程碑、工作量与验收口径不变；新增附录 D 版本锁定清单，风险表合并前后端调研风险。

## 2. 总体技术方案

### 2.1 架构原则（继承 PRD 15.1，技术实现按调研文档定稿）

1. **模块化单体优先**：后端为 Spring Boot 单应用内模块边界隔离（见 2.4），不为 MVP 拆微服务；
2. **事务与异步分离**：核心 CRUD 走 PostgreSQL 强一致；Outbox + 消息队列驱动搜索、报表、通知、集成、AI；
3. **多租户**：`tenant_id` 强制贯穿数据层（Repository Guard + MyBatis-Plus 租户拦截 + 行级策略 + 缓存命名空间 + OSS 前缀 + 自动化越权测试）；
4. **集成适配层**：统一 OAuth、身份映射、Webhook 验签、重试、幂等、限流；Git 平台是第一个 Provider（只读）；IM/消息通道 P1 自建预留；
5. **AI Gateway**：多模型路由、脱敏、配额、成本、超时、审计、回退；RAG 只检索授权对象；
6. **AI 证据链优先**：状态与进度真相由证据自动供养（活动事件 + 代码证据），AI 只产出建议草稿，写回须人工确认（AI-04/AI-05 红线不变）；
7. **单仓约束**：前端（pnpm + Turborepo）与后端（Maven）同级目录单仓交付；模块边界清晰、Outbox 模式、类型安全（前后端共享 API 类型契约，见 6）。

### 2.2 系统拓扑

```
[浏览器 Web App (React 19, Next.js 16 SPA 形态 / 备选 Vite 8)]   [Git 平台 (GitHub/GitLab/Gitee, 只读 Webhook/拉取)]
        │  REST /api/v1 + SSE                                        │  验签/限流/重试/幂等
        ▼                                                           ▼
┌───────────────────────────────────────────────────────────────────────────────┐
│          模块化单体 (Spring Boot 4.1.1 / Java 21, backend/ Maven 单仓)          │
│  Identity│Work Domain│Query&View│Notify&Integration│Analytics│AI GW│Admin&Audit │
└───────┬───────────────────────────────┬───────────────────────────────────────┘
        │ 业务写(强一致)                   │ Outbox → 事件流
        ▼                                ▼
  PostgreSQL 16+(主库/域数据, RLS)   Redis(缓存/rank/会话) ── 消息队列(Outbox/报表/AI/证据采集)
        │                                │
        ▼                                ▼
  OpenSearch(搜索/报表检索)      AI Gateway → 模型 Provider(多路由/配额/审计)
                                    对象存储(附件, 签名 URL)
```

### 2.4 模块边界（模块化单体内的包级模块）

后端以 Spring 包模块实现（`com.xieliu.agile.{identity,work,query,notify,analytics,ai,admin}`），模块间仅通过公开接口与领域事件通信，**禁止跨模块直接调用对方 Service**（见 §6 内部约定）。

| 模块 | 职责 | 禁止事项 |
|---|---|---|
| Identity & Tenant | 登录、成员、团队、角色、套餐、策略 | 不得直接写业务表 |
| Work Domain | 项目、目标、迭代、工作项、关系、评论、活动 | 写库须经领域服务，事件走 Outbox |
| Query & View | Backlog rank、看板/列表、搜索、共享视图 | 只读聚合 + 写事件回传，不直接改领域数据 |
| Notify & Integration | 站内通知（聚合/去重/深链）、Git 证据采集（只读）、Webhook 出口预留、重试/死信 | 核心业务不依赖采集/通知可用；采集器只读、只写事件 |
| Analytics | 事件消费、指标物化、报表 API、数据质量补算 | 只消费事件 + 快照 |
| AI Gateway | 权限裁剪、检索、摘要、状态推断、来源、评测、配额/成本 | 只读访问；写操作必须回流人工确认 |
| Admin & Audit | 配置、日志、导入导出、保留与删除任务 | 追加写，不可改历史 |

### 2.5 环境与发布

- 环境：`dev`（本地/开发）、`staging`（预发）、`prod`（生产，单 region，国内云）；
- 分支策略：主干开发 + 短生命周期特性分支；PR 合并需通过 CI（lint/单测/构建）+ 至少 1 人评审；
- 发布：每周候选版（周四冻结、周五发布），紧急修复走 hotfix；特性开关（Feature Flag）控制灰度；前端 Turborepo 与后端 Maven 各自独立构建、联合部署发布单；
- 数据迁移：`migrations` 与代码同仓，向前兼容；破坏性变更需两段式发布（先扩后缩）。

### 3.2 E-01 组织、身份与成员（FR-001）

| Story | 内容 | 验收要点 | 验证方式 | 估时 |

- 722 人日 ≈ **32.8 人月**（按 22 人日/月），落在 PRD 预算区间 32–36 人月；
- **v2.0 算术修正**：v2.0 汇总“E-01~E-15 = 568”按 32.4 人月倒推，与 Story 明细求和（614）存在 46 人日出入；v3.0 以明细求和为准，差异不影响范围结论；
- 按 9 人 × 16 周 × 5 天 = 720 人日满负荷计算，超出 2 人日（0.3%），由缓冲/范围微调消化（**裁剪优先级按 PRD 建议：优先削减 AI 建议范围或实时协作复杂度，绝不压缩安全、权限、审计**）；若按 8 人（640 人日）则需要裁剪约 11%。

## 5. 事件与消息模型

- **Outbox 原则**：业务写入与领域事件同一事务提交；Worker 幂等投递第三方；核心写入不依赖 IM 可用性；
- **事件字段**：`tenant`、`actor`、`source(web/api/automation/git/ai_confirm)`、`object`、`before/after`、`occurred_at`、`idempotency_key`；
- **消费者**：搜索索引、报表物化、通知、AI 上下文（摘要与状态推断）；各消费者独立位点、可回放；
- **事件清单（MVP）**：`org_created`、`repo_linked`、`project_created`、`work_item_created/updated`、`cycle_started/completed`、`commit_linked`、`release_tag_observed`、`health_update_published`、`ai_summary_generated/published`、`ai_status_suggested`、`import_started/completed`、`comment_created`、`subscription_changed`、`notification_sent`（埋点事件见附录 A）；
- **实时订阅**：`/api/v1/events/stream`（SSE）为既定实时通道（KB-04）；后端 `SseEmitter` + 事件增量合并；断线重连带 `last_event_id` 可重放；部署层需关闭 Nginx `proxy_buffering`；
- **事件保留**：不镜像完整聊天内容；只保存用户明确创建/关联的内容，降低隐私面。

## 6. API 设计规范

- 路径：`/api/v1/...`；REST 风格；分页一律 cursor（`?cursor=&limit=`）；
- 写幂等：`Idempotency-Key` 请求头（卡片、导入、回调必须携带）；
- 并发：写请求支持 `If-Match: <version>` 或响应头携带 version（WI-06）；
- 错误结构：`{ code, message, field?, details? }`；业务码分段（如 `10xxx=auth`、`20xxx=workitem`）；
- 鉴权：服务端中间件统一从令牌解析 `tenant_id + user_id + role`，注入请求上下文；所有查询经 Repository Guard 追加 tenant/scope 条件；
- 实时：`/api/v1/events/stream`（SSE）提供增量事件订阅，断线重连带 `last_event_id`；
- 内部约定：禁止直接跨模块调用对方 Service（模块外仅走事件或公开接口）；
- 前后端契约：前端 `packages/api-client` 以 OpenAPI 生成的类型化 client 与后端对齐（Zod schema 与服务端校验一致），共享 API 类型契约；
- 对外开放（FR-017）为 P1：MVP 期间保持 OpenAPI 文档自动生成与 Token 体系为 P1 预留，不提前暴露公网 API。

## 7. 通知与代码证据采集专项设计

### 7.1 站内通知中心

- 单通道（站内通知中心）+ 深链 + 权限校验；聚合（5 分钟）、去重（<1%）、偏好四档（即时/每日摘要/仅限关键/关闭），安全/权限事件不可关闭；
- 通知经由 Notify & Integration 模块，与业务写入 Outbox 解耦；无法投递追踪，管理员可见失败任务；
- 未来通道扩展（邮件/Webhook/P1 IM）走 Provider 适配层，静默时段、频控、退订追踪为适配层通用能力预留。

### 7.2 Git 证据采集

- 接入：管理员在管理后台授权 Git 平台（只读 Scope）→ token 加密存储 → `integrations` 记录；解析地址，token 失效自动告警并停用该仓库采集；
- 双通道：Webhook（验签 timestamp + signature）+ 定时兜底拉取（增量，防丢事件；国内 GitHub 不稳定时兜底拉取比例提高）；
- 事件化：commit/tag/PR → `evidence_events`（幂等键 = SHA，不重复入库）+ `source=git` 活动事件；commit message 展示前脱敏（邮箱/密钥/Token 模式）；
- 权限映射：仓库 ↔ 项目映射表为唯一权限依据（仓库可见性 ≠ 工作项权限）；未映射/未匹配提交进入"待认领"队列；
- 回填：历史提交批量导入，复用 IM-03 任务模式（异步/进度/取消/断点续跑）。

### 7.3 可靠性

- 限流（token bucket / 平台 API 配额水位）；指数退避重试（1s/5s/30s/5min…），超过进入死信（管理员可见可重放）；
- 核心业务不依赖采集成功：采集失败只影响证据新鲜度，不阻塞任何写路径；
- 证据采集与 AI 推断解耦：采集器只写事件，AI 消费者自行重试/补数据。

## 8. AI 证据链与智能更新专项设计

### 8.1 生成流程

```
触发(定时/手动) → 权限裁剪: 确定作用域与可见对象集
→ 证据收集: 活动事件 + Git 证据(evidence_events) + 当前快照(检索授权对象)
→ 事实构建: 已完成/进行中/风险阻塞/范围变化/下一步/数据缺口(每条带 object_id + 时间戳 + 新鲜度)
→ 建议层: 观点与建议分栏(标注推断与置信度)
→ 草稿入库(ai_summaries: model/prompt_version/sources)
→ 用户核验: 编辑/采纳/丢弃 → 发布/评论 → 审计差异
```

### 8.2 关键约束

| 约束 | 实现 |
|---|---|
| 权限先于检索 | 先用统一授权服务求出可见对象 ID 集合，再进检索/上下文；禁止"先检索后遮盖" |
| 事实与建议分栏 | 输出协议（JSON）拆分 `facts[]` 与 `opinions[]`；facts 必须有 `source` |
| 数据不足 | 明确输出"数据缺口"清单（缺失字段/过期工作项），不杜撰负责人/日期/进度/原因 |
| 人工确认 | 所有写操作（改状态/优先级/指派/截止日/健康度/对外发布）逐项确认 |
| 证据来源 | 事实可引用 Git 证据（commit/tag/PR，带深链）；证据脱敏后展示；仓库权限以映射表为准 |
| 状态建议 | 状态推断仅产草稿（E-17）；采纳必须走 ai_confirm 确认流；WIP commit 不作为"完成"依据（置信度分级） |
| 租户隔离 | 默认不训练；最小上下文；供应商清单与"不保留"配置可查 |
| 审计 | 保存模型、Prompt 版本、检索对象 ID、输出、用户编辑差异、反馈 |
| 配额/成本 | AI 成本率目标 ≤12% 收入；按模型路由（摘要/推断用高质量 + 低成本模型混合） |

### 8.3 评测与上线门槛

- 五类离线评测集：权限越权、时间混淆、虚构进度、冲突来源、数据不足；v3.0 增补：Git 证据越权（镜像仓库/无映射仓库）、误判完成（WIP commit 断言 Done）；
- 门槛：越权泄露 0、无来源事实 0、虚构 0（P0 红线）；数据不足类 100% 触发缺口提示；
- 每次模型/Prompt 变更走评测回归；发布记录可回溯。

### 8.4 智能状态推断（E-17）设计要点

- 输入：证据流（git + 活动事件）+ 当前状态快照；输出：结构化建议（status/risk + confidence + evidence_ids + 缺口清单）；
- 权限：与摘要同一套"先权限裁剪、后检索"；无权限对象不出现在建议或证据链接中；
- 确认流：工作项"AI 建议"面板 → 采纳（落地为常规活动事件，actor=用户、source=ai_confirm）/ 拒绝（负样本）；记录与差异见 `ai_suggests`；
- 质量：采纳率监控（目标 ≥60%）；采纳后出现矛盾证据自动提示复核；周度质量报告入评审；
- 红线：无任何无人值守写；Kill Switch 可立即下架全部未确认建议。
