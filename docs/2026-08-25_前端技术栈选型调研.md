**推荐组合:React 19 + TypeScript + 按 SPA 形态使用的 Next.js 16(备选 Vite 8 纯 SPA)+ shadcn/ui + Tailwind v4 + TanStack Query v5 + Zustand v5 + @dnd-kit + TanStack Virtual + 原生 SSE + TipTap 3 + Recharts 3。**

## 1. 背景与约束

- **产品形态**:类 Jira/Linear 敏捷项目管理 SaaS(协流 Agile),登录墙后使用,无 SEO/内容营销刚需;
- **核心交互**:看板(500 卡)、Backlog(1000 项拖拽排序)、列表、实时协作(SSE 增量 + 断线重连 + last_event_id)、评论 @提及、AI 摘要报告、报表图表(燃尽/周期时间)、全局搜索;
- **非功能**:首屏 P95 <2s、WCAG 2.1 AA、响应式 ≥768px、多租户权限严格(权限判定 100% 在后端,前端只做行/列级隐藏禁用);
- **交付约束**:16 周 MVP、前端团队 2 人;
- **后端已定**:Spring Boot 3.3.13 + Java 17 模块化单体,REST `/api/v1` + SSE(无 Node 服务端,前端无 SSR 负担)。

## 2. 框架选型:Next.js 16 按 SPA 形态使用(备选 Vite 8 纯 SPA)

### 2.1 决策依据

| 论点 | 说明 | 来源(调研摘录) |
|---|---|---|
| 登录墙后 SSR 收益趋零 | SSR/ISR/PPR 核心价值(公开首屏、SEO/爬虫可见、内容营销)在本产品全部落空;渲染策略应"按路由"而非"整站" | bejamas.com |
| 对标产品实证 | Linear = React + MobX + Rolldown-Vite,明确"无 RSC、无 fancy 框架" | performance.dev/sourcefeed.dev |
| 首屏 P95<2s 的正确杠杆 | 路由级懒加载 + 虚拟化列表 + Atomic CSS + IndexedDB 缓存 + 乐观 UI,而非服务端渲染 | webvitals.tools、algoramming.com |
| RSC 对重交互 SaaS 常是"错误工具" | 看板拖拽、SSE 实时、富文本 @提及全是客户端问题,SSR 无益甚至冲突 | datasofttechnologies.com |
| 多租户安全 | SSR 层扩大攻击面(CVE-2025-29927 类教训);鉴权/租户隔离应后置 Spring Boot | workos.com |
| 团队约束 | 2 人 / 16 周:Vite SPA 无 RSC 边界、async request API、ISR/PPR 缓存语义等复杂度 | — |

### 2.2 推荐形态

- **首选**:Next.js 16.3 App Router,产品页一律 Client Components(`"use client"`),关闭 SSR/ISR/PPR 的过度使用;Route Handler 仅作 SSE/鉴权代理;未来营销页/公开页再按需 SSR。
- **备选(若团队追求极致简单)**:Vite 8.2.2 + React 19 纯 SPA(可配 TanStack Router)。组件、状态、数据层与 Next.js 形态**完全通用**,切换成本仅在路由/构建层。
- **不建议**:TanStack Start(仍 v1 RC 非 stable)、Remix/React Router v7(偏资源型场景)、SvelteKit(bundle 最小但换语言,团队为 React/TS 背景)。

### 2.3 定稿建议

W1 用 2~3 天做最小原型(看板 + 拖拽 + SSE)分别跑 Vite SPA 与 Next.js SPA 形态,对比 TTFB/LCP/INP 与开发复杂度后,在技术评审(P-4)定稿;两形态共享全部组件/数据层代码。

## 3. UI 组件库与设计系统

### 3.1 推荐:shadcn/ui + Tailwind v4

- shadcn/ui(CLI 4.19.0)源码入库、无锁源、视觉完全可控——对 Linear 型产品,设计本身就是差异化;
- 2026-07 起新项目默认 Base UI 原语,Radix 仍受支持,React Aria 可选;底层可访问性地基好;
- 搭配 TanStack Table(headless)保持列表/看板/详情视觉统一;Recharts 的 shadcn chart 组件开箱即用;
- Tailwind v4 与 OKLCH 变量、`@theme inline` 主题定制原生契合。

### 3.2 对照结论(为何不用其他家)

| 候选 | 结论 |
|---|---|
| Ant Design v6 | 企业后台最快,但视觉辨识度过高(License 管理系统风),深度品牌定制需大量 token 覆盖 |
| MUI + MUI X Data Grid | 网格最强,但分组/Excel 导出/批量编辑在付费版;Material 视觉难做差异化 |
| HeroUI v3 | Tailwind + React Aria 可访问性好,但 2026-03 才重写,最不成熟,不宜作关键操作台底座 |
| AG Grid Community | 虚拟化/内联编辑免费,但视觉自成一套难统一;批量编辑属 Enterprise(¥) |

### 3.3 风险

1. **WCAG 2.1 AA 非开箱即得(最大风险)**:2026 实测 shadcn/Radix 组件 34/48 过 WCAG 2.2 AA,5 个有实质缺口(Combobox 键盘提交问题等)。须预留**整页专项无障碍审计**工时(对比度/focus-visible/键盘流/dialog/menu/live region/非颜色提示),对应文档 §3.7 KB-05 与 §9 可访问性要求。
2. **shadcn 上游维护靠手动**:组件源码入库,上游 bug/补丁不自动同步,需 tracker 反哺。
3. **数据网格能力需自建**:批量编辑(change-set 再提交)、虚拟化、权限级行列控制均为应用层代码;若网格密度成为主力,备选 AG Grid Community。

## 4. 拖拽、虚拟化与数据层

### 4.1 拖拽:@dnd-kit(事实标准)

- 多列看板 + 泳道 + 跨列拖拽开箱即用;core 6.3.1 + sortable 10.0.0 + helpers 0.5.0;
- **无障碍内置**:键盘 sensor、ARIA、屏幕阅读器 live region,直接对齐 WCAG 2.5.7(拖拽移动)与 2.1 AA;
- **性能**:500 卡 / 1000 项完全可控,核心手段 = memo 化最小 slot 组件 + 只传必要数据,让重渲染停在 hook 层;官方 2026 changelog 已加入"虚拟化排序"微任务批量身份变更;
- **备选**:Atlassian Pragmatic Drag and Drop(<4KB,Jira/Trello 同款),代价是手工代码与 React 集成繁琐。
- **风险**:dnd-kit 核心已 6.x 但 helpers 仍 0.5.0(pre-1.0)→ **锁版本 + 内部抽一层 dnd 封装**,重写只改一处。

### 4.2 虚拟化:@tanstack/react-virtual

- 5KB、headless、`useVirtualizer` + `measureElement` 免手写动态高度;与 dnd-kit / TanStack Query 同 headless 哲学,积分最顺;
- 备选 react-virtuoso(动态高度/分组/粘性头更省事但 17KB);
- **PoC 项**:虚拟化 + 排序 + 键盘拖拽三者叠加的协作 API 需在交付前验证。

### 4.3 服务端状态:TanStack Query v5

- 乐观更新范式:`onMutate` → cancel → snapshot → `setQueryData` → `onError` 回滚;
- SSE 增量:`setQueryData` 直接合并,配**幂等单调事件 id + last-event-id 可重放**;设周期/聚焦 refetch 兜底防缓存漂移;分页用 `useInfiniteQuery`。

### 4.4 客户端状态:Zustand v5

- 1.2KB,下载量已超 Redux;只放 UI/客户端态(主题、选中卡、筛选、乐观标志);
- **服务端数据一律交给 TanStack Query,不混入全局 store**(2026 共识:状态分类再选型);
- Linear 用 MobX 属历史技术栈选择,非 2026 一致建议(MobX ~16KB 偏重),不引入;
- 复杂派生/细粒度重渲染需求出现时可换 Jotai v2(二者可共存,不必二选一)。

## 5. 实时方案:原生 SSE

| 维度 | 结论 |
|---|---|
| 协议选择 | 后端单向推送场景,SSE 优于 WebSocket:标准自带自动重连、事件 id、`Last-Event-ID` 续传,无需心跳/排序/去重/广播基建;与文档既定 `/api/v1/events/stream` 完全吻合 |
| HTTP/2 | 已消除 6 连接/域限制,LLM token 流使 SSE 成为服务端推送主流默认 |
| 认证 | 原生 `EventSource` 仅 GET、不能加自定义 header → 后端用 cookie 认证可保留原生;否则改用 `@microsoft/fetch-event-source` 2.0.1 或 `eventsource-parser` 手写 fetch 包装 |
| 后端配套 | Spring Boot 用 `SseEmitter`(MVC)实现;需关 Nginx `proxy_buffering`;重放缓冲与 last_event_id 映射为后端主导设计,需与后端对齐 |
| WebSocket | 仅在需双向高频(如实时共写)时才值得;MVP 不引入 |

## 6. 编辑器、图表、表单与其他

### 6.1 富文本评论:TipTap 3.x

- ProseMirror 内核、headless、框架无关、扩展生态最成熟;官方 `@tiptap/extension-mention` + `@tiptap/suggestion` 原生支持 @提及;React 19 一等支持;
- 评论为**单人体编辑**(非实时共写),无需 Yjs 协作扩展,进一步降低复杂度;
- **不用**:Lexical(仍 v0.x 非 stable、无官方 @提及、schema 学习曲线高)、Slate(schema-less 几乎全自建,16 周交付不采用);
- 若未来需"同一文档多人实时共写",再引入 `@tiptap/extension-collaboration` + Yjs 及后端 provider(MVP 勿按共写设计)。

### 6.2 图表:Recharts v3(v3.10.1)

- React 原生、声明式、SVG、可 SSR;shadcn chart 底座即其薄封装;
- 数据量评估:500 卡 → 燃尽图约每天 1 点(≤ ~60 点),周期时间 ≤ 几百点,SVG 完全够用;
- 性能优化:降采样(建议 <600 点)、`React.memo`、`isAnimationActive={false}`、`dot={false}`、hover 状态外提;
- **注意**:3.8 起 `Cell` 已弃用(改用 `shape`);避开 Suspense/异步下"无限 setState"已知 bug(issue #7463);
- 极端大数据(>5k 点/近实时流式)再切 ECharts(canvas/WebGL),预留切换路径。

### 6.3 表单:React Hook Form 7 + Zod 4

- RHF 非受控(减少每键重渲染);Zod 单一 schema 同时服务客户端与后端校验,类型安全;
- 注意 `@hookform/resolvers ≥5.1` 才支持 Zod 4(实测 5.9.1);
- 300+ 字段时避免全局订阅 `formState`,用 `useController`/`useFieldArray`。

### 6.4 i18n 与 monorepo

- **i18n**:next-intl 4.13.7(zh-CN + en 双 locale,ICU 语法、middleware 地区协商、类型安全);Paraglide 包体更小但双 locale 收益不明显且集成较新;next-i18next 偏重(约 3×)不用;
- **monorepo**:pnpm workspaces + Turborepo(`apps/web` + `packages/ui`、`packages/api-client` 等 <20 包);pnpm catalogs 统一依赖版本;`backend/`(Maven)为同级目录,仅由 CI/独立任务构建,Turborepo 只编排 JS/TS 侧;规模大再评估 Nx。
