# 决策记录维护规则

Notes 保存重要决策的 What/Why、取舍和有效约束。架构调整、跨模块约定、有长期价值的复杂缺陷根因、重大方案选择或否决结论值得记录。普通文字、格式、简单 CRUD、机械重构、常规修复和临时任务通常不建 Note；但改变既有记录描述的事实时应同步该记录。

不保存任务清单、完成百分比、Sprint 或每日流水账。详细实施状态链接总入口选定的计划或任务来源。仅有实施步骤不要求建立 Note。

## 查找与事实来源

新建前先搜索活跃记录的相同主题、机制和约束。优先查 implemented，未完成设计查 proposed，比较方案时查相关 rejected，只有历史调查才查 archived。命中后核对生命周期、适用范围和当前事实；无命中可继续工作，不为使用体系而建档。不维护集中式索引，不默认全量加载。

代码与配置说明当前实现，正式需求与项目约束说明预期行为，测试与运行结果支撑验证，Note 保存设计理由。冲突时分析实现偏离、文档过时还是决策改变，不自动以代码覆盖约束。

## 路径与分类

路径：`{lifecycle}/{class}/YYYY-MM-DD-中文主题.md`。生命周期目录按首次使用创建，不添加占位文件；本 README 是自包含规则资源，不参与分类。

日期是主题首次提出日期，状态转换不改日期。历史日期未知则用补录日期，在“上下文”标明补录，不推测时间。topic、文件名中的主题部分及一级标题必须使用简短中文；必要的数字、版本号或不可替代的技术标识可以保留，但不能使用纯英文 topic。同日独立决策用更明确的中文主题区分，不用“记录1”“新建”“最终版”“最终版2”等无意义名称。不引入独立编号或注册表。新建文档和本次修改 topic 的文档执行本规则；未纳入本次调整的历史文档不批量改名。

| Class | 主要决策对象 |
| --- | --- |
| feature | 产品或系统能力 |
| bug-fix | 有长期技术价值的缺陷根因、复发机制或修复取舍 |
| simplification | 删除、合并、简化或收缩能力 |
| architecture | 模块边界、数据模型、认证结构、运行时机制等系统结构 |
| process | 发布、包管理、工具、政策、Agent 规范等工程流程 |
| testing | 测试策略、基础设施、隔离方式与环境设计 |

一份 Note 只选一个主要分类，不按技术栈重复归类。不随意新增 backend、frontend、database、security、misc、other；现有分类长期无法表达需求时，先调整本规则及已有检查规则再增加类别。

## 生命周期

标题之后写 `Status`，必须与路径生命周期一致。

| 生命周期 | 含义及边界 |
| --- | --- |
| proposed | 尚未完整交付；Decision state 为 pending（待决定）、accepted（采用但未全部实施）、partial（部分落地，写明边界）、deferred（暂缓，写原因、恢复条件及未知恢复时间） |
| implemented | 范围已经落地、仍指导当前实现，必要验证已完成且依据可追溯；用现在时描述实际方案 |
| rejected | 明确不再采用且否决理由有长期价值；保留原提案，说明理由及重新考虑条件 |
| archived | 曾生效而现已完全失效的 implemented 历史快照；不因旧、长或低频而归档 |

暂缓不等于拒绝或归档。必要验证受环境限制时保留 proposed，说明已完成与缺口；不能把代码已写、测试已存在写成验证已执行。

确有交付事实的历史决策可直接补录 implemented，注明事实来源、补录背景和无法确认的历史验证。本次开发尚未完成必要验证的工作不得借历史补录绕过迁入条件。未知理由、选项、评审或测试结果写“未记录”或“无法确认”，不要编造。

## 更新还是另建

- 路径、符号名或事实描述变了，核心决策与理由未变：同一变更更新原记录，不追加流水账。
- 新的重要未实施决策：新建 proposed；重要方案、约束或主要理由改变：另建并关联旧记录，不原地反转旧决策。
- 部分替代：旧记录保留活跃并明确剩余适用范围，双方交叉引用。
- 完整替代：新方案完整落地且旧约束全部失效后才归档旧记录。检查兼容行为、持久数据、配置及约束，不能仅看主要代码删除。新提案未落地时旧 implemented 仍有效。
- rejected 重新评估：另建 proposed，关联旧拒绝结论；普通落选选项放在所属 Note 的“已考虑的替代方案”，不必独立建档。

不自动合并或删除历史记录，已有旧分类或旧目录按当前授权范围处理。

## 转换与链接

proposed → implemented：确认范围交付与必要验证；将“提案”改成实际“决策”，整理真实理由与后果，把“完成条件”改为“验证”中的实际依据，剔除临时任务。范围收缩时说明原因、边界及未交付事项去向，不能删条件制造完成。按本文件的 implemented 契约与骨架整理正文，更新 Status、路径、链接，并复核旧记录有效性。

proposed → rejected：保留原提案全部正文与章节顺序，在末尾补充“否决理由”和“重新评估条件”；更新 Status、路径和引用。不能把原提案改成获选方案。

implemented → archived：确认全部失效，保留原正文，头部改为：

```markdown
# <原决策标题>

Status: archived
Previous status: implemented
Archived: YYYY-MM-DD
Archive reason: 失效原因
Superseded by: [<替代决策标题>](<替代记录的相对路径>)
```

无替代记录时省略 Superseded by；上述文件头后空一行，保留原正文。

交叉引用使用相对 Markdown 链接。移动前定位活跃文档的入站链接，移动后在同一变更中修正这些活跃链接及被移动文档仍需维护的出站链接，同时完成正文、状态、范围与替代关系维护。活跃文档引用归档记录时标明历史依据并保证目标存在；只读发现或无法访问的外部链接不冒充本地验证。

归档后正文冻结，不随代码或规范变化重写；既有归档正文中的历史出站链接不要求跟随仓库演化修复，也不因这些历史链接失效而回写归档文件。移动当次造成的活跃入站链接、归档记录对外的必要链接和活跃文档指向必须在冻结前检查。历史错误在活跃记录中注明并引用原文，不静默改写旧结论。仅 implemented 可进入 archived，不因暂缓把 proposed 归档。

## 格式与证据

### 文件格式契约

适用于按本规则创建的 Note 的后续维护，以及本次明确授权纳入本契约或转换的活跃 Note。已有项目定制格式先沿用其规则，接入不隐式迁移历史；archived 保留封存时正文，不追溯套用新格式。规则文件及其中的骨架示例、接入片段不作为 Note 检查。

- 使用 UTF-8 Markdown，LF 或 CRLF 均可，文件末尾换行。全文只有一个一级标题，不使用 YAML frontmatter。代码围栏内示例不计入字段或章节检查。
- 第 1 行为以 `# ` 开头的非空一级标题，第 2 行空白，第 3 行为唯一的 `Status: <lifecycle>`。值只能是 proposed、implemented、rejected、archived，必须与目录一致，不附加日期、理由或括号说明。
- proposed 第 4 行必须为唯一的 `Decision state: <state>`，值只能为 pending、accepted、partial、deferred；其他状态不得保留该字段。元数据之后空一行，再开始正文。
- archived 第 4—6 行依次为 `Previous status: implemented`、`Archived: YYYY-MM-DD`、`Archive reason: <非空原因>`；之后可有唯一的 `Superseded by: <相对 Markdown 链接>`，再空一行开始原正文。归档日期必须是真实日历日期；归档字段不得出现在活跃文件头。
- 标准二级标题必须逐字使用中文名称、各出现一次并保持下表相对顺序。可选章节省略后不留空标题。允许在“上下文”之后增加有内容的专用技术章节，不得替代或重复标准章节，也不得绕过状态禁止项；“参考资料”的位置仍遵守下表。
- 正文第一个二级标题必须是“上下文”，独立描述问题、范围和约束，不能只重复解决方案。

| 状态 | 必填二级章节（顺序） | 可选章节及位置 |
| --- | --- | --- |
| proposed | 上下文 → 提案 → 理由 → 已考虑的替代方案 → 完成条件 → 风险与待解决问题 | 参考资料在末尾 |
| implemented | 上下文 → 决策 → 理由 → 已考虑的替代方案 → 影响 → 验证 | 约束在“影响”与“验证”之间；参考资料在末尾 |
| rejected（直接记录否决） | 上下文 → 提案 → 否决理由 → 已考虑的替代方案 → 重新评估条件 | 参考资料在末尾 |
| rejected（由 proposed 转换） | 保留原提案全部章节及顺序，必须仍有“上下文”“提案”“已考虑的替代方案”；在原正文末尾增加“否决理由”“重新评估条件”，各一次 | 保留原“参考资料”位置 |
| archived | 保留归档前正文，不按活跃骨架重新整理 | 不新增正文章节 |

- 必填章节必须有事实内容或明确的未知说明及原因，不能仅有空白、注释、TODO、TBD、待填写或模板提示。“已考虑的替代方案”逐项说明真实比较的方案及未采用原因；无可靠记录时写“未记录”或“无法确认”及背景，不编造，也不删除本节。
- proposed 的“完成条件”必须给出可观察结果。partial 在“提案”中写明已交付与未交付边界；deferred 在“风险与待解决问题”中写原因、恢复条件及恢复时间（未知写待定）。
- implemented 用现在时描述实际方案。禁止二级标题“提案”“计划”“迁移计划”“验收标准”“完成条件”“风险与待解决问题”，以及对应的旧英文标题 Proposal、Plan、Migration plan、Acceptance criteria、Completion criteria、Risks and open questions（英文大小写不影响判断），也不得用同义标题保留待执行计划。历史说明可用过去时，未交付事项只说明边界和去向。“验证”必须有实际证据或可靠报告链接；历史补录明确无法确认的验证，不伪称本次执行。
- rejected 转换时保留原验收条件、风险、技术细节和理由，不按直接记录否决骨架裁剪正文。转换后原提案不随实现演化重写；重新评估另建 proposed，历史错误以明确的补充说明纠正并保留原判断。暂无重新考虑条件时如实说明。
- 除规定字段外，不新增文件头字段；额外背景放正文。专用章节标题不得重复。归档冻结后的历史例外以封存时契约为准。

### 格式检查与转换验收

依次核对路径与真实日期、文件头及字段唯一性、章节及顺序、非空内容、状态禁止项、转换保真和引用。报告违规文件、行号或章节、规则及修正方向。必填缺失、非法状态、重复字段或标题、写作提示残留、转换丢失原文、悬空本地链接均为不通过；未核对项写“未检查”。格式通过不代表实现或验证事实正确。

proposed 转 implemented 删除 Decision state 并满足目标骨架；转 rejected 删除 Decision state、保留原文并补否决章节；implemented 转 archived 只调整归档元数据和封存前必要链接。同次完成正文、状态、路径及引用变更。暂缓只更新 Decision state 及原因，不迁入 rejected 或 archived。

按本文件下方对应状态的最小骨架生成正文，不依赖独立模板。直接记录否决用 rejected 骨架；由 proposed 转换遵守保真规则。archived 保留原正文，只使用上方归档文件头规则。可选章节按契约和实际内容增补；必填章节不得删减，保留判断决策所需事实，不为填满章节编造内容。

新增交付决策必须有必要验证的可追溯依据，写入“验证”，可在该节链接可靠报告。记录检查内容、实际结果及时间或提交，说明未验证项；历史通过不代表本次执行通过。流程决策可用适用检查证明，不强制无意义测试。历史判断尽量链接具体提交或稳定证据。

结束检查：分类、状态、日期、范围、替代关系、必要证据及链接一致。结构检查不能证明决策正确或测试执行；必须核对实际事实。Work 结束不自动使 Note 成为 implemented，Work 归档也不表示决策失效。


## 最小骨架

以下代码围栏是本规则的组成部分，初始化复制本 README 时保留；生成实际 Note 时替换尖括号内容，按上方契约补充事实与必要的可选章节，不将占位内容当成交付。完整格式和状态转换以上方契约为准。

### 提案骨架

```markdown
# <决策标题>

Status: proposed
Decision state: pending

## 上下文

<问题、背景、适用范围和约束>

## 提案

<拟采用方案；partial 时写已交付与未交付边界>

## 理由

<选择依据和关键取舍>

## 已考虑的替代方案

<真实考虑过的方案及比较理由；无法确认时说明原因>

## 完成条件

<代表本决策范围已交付的可观察结果>

## 风险与待解决问题

<风险与未知；deferred 时说明原因、恢复条件及恢复时间>
```

### 已实施骨架

```markdown
# <决策标题>

Status: implemented

## 上下文

<问题、背景和适用范围>

## 决策

<现在时描述当前实际采用的方案>

## 理由

<采用原因和关键取舍>

## 已考虑的替代方案

<真实替代方案及未采用原因；无法确认时说明原因>

## 影响

<收益、代价、限制与放弃的能力>

## 验证

<实际检查、结果、时间或提交、证据与未验证边界>
```

需要长期约束时，在“影响”与“验证”之间增加“约束”；需要其他依据时在末尾增加“参考资料”。历史补录遵守生命周期中的证据边界。

### 已否决骨架（直接记录否决）

```markdown
# <决策标题>

Status: rejected

## 上下文

<当时的问题、背景和约束>

## 提案

<原提案，不改写为获选方案>

## 否决理由

<未采用原因及结论依据>

## 已考虑的替代方案

<实际比较过的其他方案；无法确认时说明原因>

## 重新评估条件

<值得重新评估的条件；没有已知条件时如实说明>
```

由 proposed 转为 rejected 时不重新生成上述正文：删除 Decision state、更新 Status，保留原提案全部正文及章节顺序（包括原“参考资料”位置），只在末尾补充“否决理由”和“重新评估条件”。
