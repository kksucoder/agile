# 项目任务系统架构

Status: proposed
Decision state: accepted

## 上下文

项目拟先交付类似 Trello 的最小任务看板，未来由 Agent 查询及修改项目任务，并可能发展为多人使用的长期后端服务。截至 2026-09-24，仓库尚无业务实现，`backend/` 仅有 `.gitignore`。当前没有已知的用户规模、部署环境、团队语言约束或现有服务集成要求；MVP 默认本地单实例、单用户使用。

## 提案

前端采用 React、TypeScript 和 Vite；后端采用 Java 与 Spring Boot，提供版本化 HTTP API；持久化采用 PostgreSQL。前端及未来的 Agent 适配层调用同一应用服务，不让 Agent 直接访问数据库。MVP 先提供项目、看板、列和任务的基本操作；Agent 工具协议、用户认证、多人协作和后台执行能力在有明确需求时接入，不作为本次 MVP 的交付范围。业务服务与 HTTP 控制器、数据访问层分离，任务移动及排序在数据库事务内完成。

## 理由

该产品的长期难点更可能是项目权限、并发修改、操作审计与 Agent 写入边界，而不是页面渲染。稳定的服务接口和关系型数据约束能支撑这些能力。Spring Boot 提供 Web 服务及后续生产运维能力；PostgreSQL 适合未来多用户并发访问。直接选用目标后端技术，避免在 MVP 验证后仅为统一服务体系而重写；第一阶段仍限制交付功能。Agent 接入通过应用服务复用业务规则，协议层可独立增加。

## 已考虑的替代方案

- React + Fastify + SQLite：适合本地单用户快速验证，前后端同用 TypeScript；若长期方向是多人服务，后续仍需迁移数据存储并补齐权限和运维能力。Fastify 本身可以承载该系统，但当前已明确希望保留发展为较大后端服务的空间，因此本方案不优先采用。
- 纯前端浏览器存储：部署最简单，但难以给浏览器外的 Agent 提供统一的任务接口和业务规则，因此不采用。
- 一开始拆分多个微服务：目前没有独立部署、吞吐或团队边界的证据，增加分布式一致性与运维负担，因此先采用单体服务。

## 完成条件

- React 界面与后端 HTTP API 使用同一套项目和任务语义；刷新页面后数据仍在 PostgreSQL 中。
- 项目、任务及任务移动通过后端应用服务完成；跨列移动与排序具备事务一致性，过期版本的修改返回明确冲突。
- API 可由浏览器以外的客户端调用，并以稳定 ID、结构化错误和明确版本字段表达结果，为后续 Agent 适配保留入口。
- 约定的 MVP 范围和必要验证完成后，再依据实际代码与测试证据将本记录转为 implemented；仅有方案文档不能视为已实施。

## 风险与待解决问题

- 首批用户规模、是否需要局域网或公网访问尚未确认。MVP 按本地单用户设计；开放给其他用户或 Agent 主机前，必须补齐身份认证、项目授权和操作审计。
- Agent 的具体宿主、调用协议和可写操作权限尚未确定。MVP 只固化领域服务与 HTTP 接口；接入时再确定 MCP 或其他适配方式，不把协议假设写进核心模型。
- PostgreSQL 增加本地运行依赖；实施计划需提供可重复启动的开发环境及真实数据库验证，不能以其他数据库的测试结果替代。
- 看板按状态分列、项目为任务可选关联的产品模型见[任务状态看板与项目关联](2026-09-28-任务状态看板与项目关联.md)；本记录中的技术栈、服务边界与未来 Agent 接入原则继续适用。
