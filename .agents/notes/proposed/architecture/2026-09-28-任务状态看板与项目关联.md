# 任务状态看板与项目关联

Status: proposed
Decision state: accepted

## 上下文

现有 MVP 计划将看板设计为每个项目一块、每个项目有三列，任务必须归属项目和列。用户于 2026-09-28 补充：任务看板按任务状态归纳，任务可以与项目关联。所附界面参考图显示 To Do、On Process、On Review、Completed 四个状态列表。该说明改变看板与项目的关系，现有数据库迁移中的必填 `project_id` 和 `board_column` 模型不能直接表达无项目任务。

## 提案

- 看板以任务为中心，按固定状态“待办、进行中、待审核、已完成”展示活动任务；项目是可选关联，不决定任务所属的状态列表。完成与归档是不同概念，归档任务不出现在活动看板。
- 任务具有稳定 ID、状态、状态内排序位置、可空的项目 ID、标题、描述、版本及时间字段。项目仍可创建、列出和重命名；看板可查看全部任务，也可按项目筛选。无项目任务在未筛选的看板中正常显示。
- 状态内位置按全局看板维护。按项目筛选只改变可见任务，不另建项目专属排序。修改任务状态、位置或项目关联由同一应用服务处理；状态移动与位置调整在事务中完成，并明确并发冲突。
- API 以全局看板及任务资源为中心，项目 ID 在任务创建和编辑时为可选字段。前端与未来 Agent 适配层使用相同业务规则。现有已执行的 Flyway V1 迁移不原地改写；通过后续迁移调整表结构。
- 参考图的截止日期、里程碑、负责人、优先级、链接与评论等卡片信息尚未被明确要求为 MVP 功能，后续逐项确认。

## 理由

状态是看板的分组依据，项目是任务的附加维度。将项目关联设为可选，使独立任务与项目任务能在同一看板展示，且筛选不改变任务状态。固定状态足以覆盖当前参考图，避免在 MVP 中引入尚无需求的自定义工作流。保留应用服务及事务边界，可复用既定的 HTTP API 与未来 Agent 接入方式。

## 已考虑的替代方案

- 继续为每个项目建立独立三列看板：无法直接展示无项目任务，也与用户说明的按任务状态归纳不符，因此不采用。
- 建立一个隐藏的默认项目容纳独立任务：数据库仍把项目作为必填归属，给筛选及接口语义带来额外例外，因此不采用。
- MVP 即支持自定义状态和各项目独立排序：增加配置、迁移及并发语义，当前参考图和说明未要求，因此暂不采用。

## 完成条件

- 全局看板按四种状态展示任务；有项目与无项目任务都能创建、编辑、移动、归档，项目筛选不改变状态及全局位置。
- 数据库、应用服务、API、前端及验证使用一致的状态和可选项目语义；已有 Flyway V1 数据库能通过后续迁移升级。
- 在真实 PostgreSQL 中验证状态移动、排序、项目筛选、无项目任务、版本冲突与异常回滚。

## 风险与待解决问题

- 四个状态名称来自参考图；若用户希望自定义状态、不同项目工作流或独立排序，需要另行确定产品规则。
- 全局排序在筛选视图中可能出现非连续的可见位置；界面应按全局顺序展示，筛选视图拖拽如何映射回全局位置需在实现前明确。
- 现有 V1 迁移已按项目列模型创建表。后续迁移应处理已有项目、列和任务数据的映射；当前仅确认仓库有骨架，不能假定所有运行环境都没有业务数据。
