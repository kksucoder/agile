# 实施规划维护规则

Work 保存一项可独立验收、需要持续管理的工作的实施上下文。长期设计理由归 Note，任务来源以项目总入口为准。规划不自动授权业务开发；已授权实施时按依赖推进，不因建档新增确认。

## 是否建档

按顺序判断，能复用时不新建：

1. 活跃工作范围内的小问题：更新对应任务或证据，不另建目录。
2. 已有计划、Issue、Jira 或任务记录覆盖：更新原来源，不复制状态。
3. 无既有任务归属的小修复、局部调整且一次可完成：不建 Work，在交付说明中记录修改与验证。
4. 必须跨会话保存实施上下文，或需持续协调复杂依赖与验收，且没有合适来源：先建单份 plan.md，内含简短任务表。
5. 单 Plan 已不能清楚表达依赖与分别验收：才拆出 tasks.md；把任务状态移过去，Plan 仅链接，不保留第二份清单。

文件多、测试多、步骤多或普通先后关系都不足以触发建档。验证环境受阻时优先在既有来源记录；没有来源且需要后续恢复才建最小 Plan。用户明确要求规划文件时按下节交付，不额外生成受管理 Work。骨架存在不表示必须实例化。建立 Work 不自动建立 Note。

## 独立规划文件

用户明确指定单份规划文件的路径或名称，或只要求输出规划文档时，按用户指定的位置、名称和已有格式交付；没有指定格式时可采用本 README 的 Plan 契约。此模式是一次规划交付，不自动创建 `.agents/work/README.md`、`active/` 或 `archived/`，不强制把文件放入固定的 `active/YYYY-MM-DD-中文主题/plan.md` 路径，不自动生成 `tasks.md`、归档目录或入口链接。文件完成后按用户指定来源保留或移交，不因完成而强制移动或归档；其他已有 Notes、Work 和外部任务来源的生命周期不因独立规划改变。

若用户随后明确将独立规划纳入受管理 Work，再按本节的结构、状态、依赖和收尾规则处理；已有正文和状态先比较，保留定制并记录必要的迁移依据。

## 结构与职责

新工作使用 `active/YYYY-MM-DD-中文主题/plan.md`；必要时同目录放 tasks.md。日期是首次建档日期，归档不变；topic、目录名中的主题部分及 Plan、Tasks 的一级标题必须使用简短中文；必要的数字、版本号或不可替代的技术标识可以保留，但不能使用纯英文 topic。同日独立工作以更具体的中文主题区分。新建文档和本次修改 topic 的文档执行本规则；未纳入本次调整的历史文档不批量改名。`plan.md`、`tasks.md` 是固定契约文件名，不翻译。未使用目录不创建、不添加占位文件。

| 文件 | 唯一维护的信息 |
| --- | --- |
| plan.md | 目标、范围、非目标、实施方案、阶段、验证策略、验收、整体状态；单文件模式也保存任务 |
| tasks.md（可选） | 任务编号、依赖、状态、完成条件、验证证据与阻塞原因 |
| 关联 Note（按需） | 决策、理由、替代方案与长期约束 |

任务完成条件细化 Plan 验收，不另立冲突范围。不维护完成百分比、progress.md、status.md、daily-log.md、completion.md 或重复日志。

开始实施前 Plan 至少明确目标、范围、非目标、验收，足够启动即可。方案交代实施顺序、模块边界、接口或数据变化，涉及迁移则交代兼容与回退。重要理由链接决策，不复制。

## 状态、依赖与证据

Plan Status：planned、in-progress、blocked、completed、cancelled、superseded。后三项是结束状态。整体暂缓用 blocked，注明原因、影响、恢复条件及恢复时间；未知写待定。任务 blocked 不自动把 Plan 置为 blocked：只要仍有不依赖该任务且可安全推进的工作，Plan 保持 in-progress；只有没有可推进的任务，或该阻塞直接阻止整体验收时，Plan 才为 blocked。只读查找、读取或引用外部事实属于发现，可继续执行；访问失败只限制相关证据。只有写入外部系统、破坏性移动或删除、未经授权的迁移，或会改变下一步交付的未决业务选择，才暂停受影响步骤。`planned` 表示尚未开始实施且没有计划级阻塞；`in-progress` 表示已有工作进行中，或仍有可独立推进的未完成任务；`blocked` 表示当前没有可安全推进的步骤，或阻塞直接影响整体验收；`completed` 只表示约定范围已经验收，`cancelled` 和 `superseded` 必须说明未完成范围的去向，不能伪称原验收完成。

任务状态：todo、in-progress、blocked、done、cancelled。正常执行 todo → in-progress → done；in-progress 与 blocked 可互转；尚未开始即受外部条件阻塞也可 blocked。正常等待前置任务可保留 todo，用依赖说明条件。未结束任务可 cancelled，写明原因及去向，不计作完成。

- done 要求完成条件满足，必要验证已执行且有证据。代码完成、测试存在、测试执行通过是不同事实，验证受阻不能标 done。
- blocked 说明缺少什么、影响范围和解除条件；可继续不依赖它的独立任务。
- 工作内编号用 T01、T02 等，唯一且取消后不复用。依赖写本工作编号或外部稳定来源，无循环依赖。前置结果未满足时不开始依赖工作；前置被取消也不能自动解锁后续任务，须重新判断依赖。
- 活跃任务发现范围内遗漏或原验证无效，可 done → in-progress/blocked，保留原证据并说明返工原因，复核依赖任务与整体状态。未归档但已 completed 的 Plan 同步恢复为 in-progress/blocked，不能沿用失效结论。

按可独立判断完成的结果拆任务，不按文件拆分。任务至少记录状态、必要依赖、完成条件及证据或阻塞原因；条件不能只写“完成代码”。使用固定列名的简表，复杂任务才展开任务卡，同一任务不要同时维护两份状态。

证据至少包含检查内容或必要命令、实际结果、对应时间或提交，以及必要链接和限制。跨会话证据保存在项目可访问的文档或已有报告，不只写“上次聊天已通过”。Plan/Tasks 可以链接或简要引用 Note 的决策，但不复制 Note 的状态；Note 可以链接 Work 的实施证据，但不维护任务状态。各来源只维护自己负责的事实。不预填成功，不记录每次运行、普通调试或每日流水账；有诊断价值的失败可简述原因和修复结论。

## 恢复、调整与收尾

开始或恢复工作时读实际存在的 Plan、Tasks，核对范围、证据和可执行依赖，再按需读关联决策。没有 Work 就沿用既有来源，不为恢复流程临时补建。任务完成或实质阻塞时更新，不要求每次编辑都写日志。

Plan 随实施更新为当前有效方案。实质范围调整简述改变、理由、影响哪些验收项；未完成项必须明确继续、取消、暂缓或转移去向，不删条件制造完成。普通措辞变化不追加历史日志。

收尾按以下顺序：

1. 对照验收与实际证据；只有约定范围已验收才标 completed。必要验证未完成不能标 completed。
2. 处理所有未完成任务，保留取消理由、继续或转移来源链接；仍属本次且未验收的工作保持活跃。取消不是完成，范围变更须有依据。
3. 同步受影响的既有决策，无新决策不强制建 Note；Work 完成不能替代 Note 自身的 implemented 条件。
4. Plan 记录结束结论与必要验证摘要，cancelled 或 superseded 不宣称原验收已完成，写明原因与后续去向。
5. 受管理 Work 的整个工作目录移入 archived，保持名称，修复活跃入站链接及移动后受影响的出站链接。独立规划文件不按本条强制移动或归档。结束状态与文档正文、证据一致后才归档。

Work archived 表示工作结束，原因由 Plan 状态说明；Notes archived 表示决策失效，两者独立。历史任务不是当前待执行清单，历史计划也不是当前架构依据。

归档后不重启旧任务。后续问题重新按建档条件判断，可更新现有来源或交付说明；确需建档时建立后续工作并关联历史，不因引用归档就强制新建。纠正历史事实时明确记录纠正及依据、保留原结论可追溯性，不追随代码变化重写历史完成状态。

## 文件格式契约

以下规则用于受管理 Work 的新建文件和本次授权调整的文件。用户指定的独立规划文件按用户位置、名称和格式交付，不因本规则强制进入固定 Work 目录、生成配套 Tasks 或迁移归档；已有外部计划或任务系统沿用其格式，不强制改名、复制或迁移。以下固定文件名与目录仅约束本体系的受管理 Work 文件。

### 共用语法

使用 UTF-8 Markdown，LF 或 CRLF 均可，末尾换行。每份文件只有一个以 `# ` 开头的非空一级标题，不使用 YAML frontmatter。Plan 的标准二级标题使用下表原名，各一次、按相对顺序排列；必填章节不得合并或省略，可选章节无内容时删除。Plan 允许在第一个必填章节之后插入有实际内容的专用章节；有“相关文档”时放在它之前，不得重复标准标题或另建状态清单。代码围栏内示例不计入格式检查，交付正文不得只剩空白、注释、TODO、TBD、待填写或模板提示。

### plan.md

第 1 行为实际工作标题，第 2 行空白，第 3 行为唯一的 `Status: <state>`，第 4 行空白；state 仅允许 planned、in-progress、blocked、completed、cancelled、superseded，不附加原因或日期。文件头不增加其他字段；背景、阻塞及时间写入正文。

| 必填章节（顺序） | 可选章节及位置 |
| --- | --- |
| 目标与背景 → 范围与非目标 → 实施方案 → 依赖与风险 → 验证策略与验收条件 → 任务 | 范围调整在任务之后；结束结论在范围调整之后（省略范围调整时紧随任务）；相关文档在末尾 |

- 范围与非目标分别交代包含与不包含的工作；无外部依赖或已知风险时明确说明，不删除依赖与风险。
- 验证策略与验收条件同时说明可观察的完成结果与验证方法；未知细节写明影响，不能以未知代替已完成的验收。
- 单文件模式的任务章节使用下述统一任务表；需要展开时使用任务卡。同一任务只出现于一种表示中。
- 双文件模式的任务章节只链接同目录 tasks.md，可说明拆分原因，不重复任务 ID、逐项状态或完成条件；整体 Status 仍由 Plan 维护。
- blocked 在依赖与风险中写原因、影响、恢复条件及恢复时间（未知写待定）。
- 实质范围变化必须有范围调整，记录理由、受影响验收及未完成事项去向。
- completed、cancelled、superseded 必须有结束结论，其他状态不得有该章节。completed 写实际验收及证据；cancelled、superseded 写原因、已完成边界与未完成事项去向，替代来源存在时必须链接，不伪称原验收完成。
- 从结束状态恢复为活跃状态时移除结束结论章节，将仍有用的历史证据及恢复原因保留在范围调整或对应任务中，不删除证据；归档文件不得按此方式重启。

### tasks.md 与内嵌任务

tasks.md 第 1 行为实际任务集标题，第 2 行空白，第 3 行固定为`实施范围与验收条件见 [Plan](plan.md)。`，第 4 行空白；不设置文件级 Status 或另写整体验收。正文只承载任务表或任务卡，不添加整体方案和结束总结。

统一任务表列名与顺序固定为：任务、状态、依赖、完成条件、验证依据或阻塞原因。第一列为“任务编号 空格 非空标题”；其他列不得为空，无依赖写“无”，未验证写“尚未验证”。本工作任务编号匹配 T 加至少两位数字（如 T01、T100），按需分配；同一工作内唯一，取消后不复用。单 Plan 和 Tasks 的编号语义一致。

任务卡使用三级标题`### T01 任务标题`，以下字段各出现一次并按此顺序排列：

1. 状态：必填，值为 todo、in-progress、blocked、done、cancelled。
2. 依赖：必填，写编号或外部稳定来源；无依赖写“无”。
3. 工作内容：可选，说明可观察结果，不重复完成条件。
4. 完成条件：必填，可独立判断的结果。
5. 验证依据：必填，写实际结果或“尚未验证”及已知限制。
6. 阻塞或取消原因：blocked、cancelled 必填，其他状态不保留该字段；写原因、解除条件或去向。

任务表与任务卡可混用，但同一任务不得重复出现。表中 blocked、cancelled 的必要原因写在最后一列。done 的证据必须包含实际检查内容或命令、结果、对应时间或提交及必要限制，可链接可靠报告；状态值不得附加解释。依赖必须解析到实际任务或可识别的外部来源，不允许自依赖、循环依赖或以取消自动解除依赖。

### 检查结果

依次检查文件头、章节、任务表示唯一性、字段与状态、依赖、证据、相对链接及 Plan/Tasks 一致性。违规报告文件、行号或任务编号、规则及修正方向；缺必填项、非法状态、重复维护、自依赖或循环、未验证却标完成、悬空本地链接为不通过。未核对的证据写“未检查”；格式通过不能证明验收已执行。骨架中的示例任务和占位内容必须替换为实际内容，不能把示例当成已创建任务。

## 生成与检查

按本文件的 Plan 最小骨架生成；仅需拆分时生成 Tasks，并将 Plan 的任务章节改为链接。保留必填章节及顺序，只移除契约允许省略的无内容可选章节，不预填结束结论，不依赖独立模板。

检查整体状态与任务验收是否一致、依赖是否可执行、证据是否可访问，以及相对链接、移动后路径和单一状态来源。结构检查不能证明实际验收执行；依事实审查。一个工作可关联多份 Note，一份 Note 可被多个工作引用，但不重复维护理由或进度。

### 任务卡骨架

仅复杂任务需要展开时使用；可以与表格混用，但须先移除表中同一任务。下例展示 todo 的必填字段及可选工作内容；blocked、cancelled 时在验证依据之后增加“阻塞或取消原因”，其他状态不保留该字段。

```markdown
### T01 <任务标题>

- 状态：todo
- 依赖：无
- 工作内容：<需要实现的可观察结果；无必要时省略此字段>
- 完成条件：<可独立判断的结果>
- 验证依据：尚未验证
```
