# 项目任务管理 MVP 设计与实施计划

Status: in-progress

## 目标与背景

交付一个可在浏览器中使用的最小任务看板：用户能够创建任务、按状态查看和移动任务，并可选择将任务关联到项目，数据持久保存。未来 Agent 应能通过受控接口读取和操作相同的任务，但本阶段先验证人工使用的完整闭环。仓库已有后端骨架和按项目列建模的 Flyway V1 迁移，尚无业务服务、API 或前端；已执行 V1 的数据库须通过后续迁移升级。长期技术选择见[项目任务系统架构](../../../notes/proposed/architecture/2026-09-24-项目任务系统架构.md)，产品模型见[任务状态看板与项目关联](../../../notes/proposed/architecture/2026-09-28-任务状态看板与项目关联.md)。

## 范围与非目标

**范围**：单用户、本地单实例；创建、列出、重命名项目；创建、查看、编辑、归档任务，任务可不关联项目；全局看板按“待办、进行中、待审核、已完成”四种固定状态分列，可按项目筛选；状态内排序及跨状态移动；页面刷新后保持数据；提供供网页和外部客户端调用的 HTTP API。任务字段限标题、描述、可选项目关联、状态、位置、版本及创建和更新时间。归档时间用于区分已归档任务，状态“已完成”不等于归档。

**非目标**：账号与团队权限、项目成员、评论、附件、截止日期、里程碑、负责人、优先级、提醒、搜索、实时协作、自定义状态或复杂工作流、Agent 自主执行、MCP 服务端及公网部署。删除任务按归档处理，MVP 不提供归档任务恢复界面。参考图中的其他卡片信息尚未确认为本阶段需求，不以占位页面冒充交付。

## 用户场景与交互

用户打开按状态分列的全局看板，可在任一状态新增有项目或无项目任务，打开任务编辑标题、描述及项目关联，拖拽改变状态或状态内位置，并将任务归档。用户可按项目筛选任务，也可创建、列出和重命名项目；无项目任务在全局看板可见。保存失败时界面应保留可理解的错误并重新获取服务端状态；版本冲突时不得静默覆盖另一端的修改。状态名称固定，MVP 不支持自定义状态。参考图只确定状态分列的布局方向，其他卡片字段不据此自动进入范围。

## 数据与接口设计

核心数据为 `project` 与 `task`：主键为稳定 UUID；项目包含名称、版本及创建和更新时间；任务包含可空的 `project_id`、固定状态 `status`、状态内整数 `position`、`version`、`created_at`、`updated_at`、可空的 `archived_at`。项目关联存在时由外键保证有效；状态值、非空标题、非负位置和版本由数据库约束保证。状态列表是任务状态的视图，不按项目创建列记录。任务移动在事务内调整源状态和目标状态的全局位置，并递增受影响任务的版本；归档后活动任务排序应保持正确。按状态读取时按位置排序；项目筛选只改变可见集合，不改变全局位置。现有 V1 的 `board_column` 与必填任务项目外键须通过新的 Flyway 迁移转换，不修改已执行的 V1 文件。

HTTP API 以 `/api/v1` 为前缀，最小契约如下；请求和响应均为 JSON，时间使用带时区的 ISO 8601 字符串。修改任务需提交 `expectedVersion`，版本不符返回 `409`；参数错误返回 `400`，资源不存在返回 `404`。移动操作的 `targetIndex` 从 0 开始，表示移动完成后在目标状态全局列表中的位置。项目筛选视图的拖拽映射须在实现前明确，不将可见列表索引直接当作全局索引。

| 方法与路径 | 用途 | 关键输入或输出 |
| --- | --- | --- |
| `GET /projects`、`POST /projects` | 列出、创建项目 | 项目 ID、名称；创建输入为名称 |
| `PATCH /projects/{projectId}` | 重命名项目 | 名称、`expectedVersion`；项目也保留版本字段 |
| `GET /board` | 获取全部未归档任务，可按项目筛选 | 按固定状态分组，状态内按全局位置排序；筛选不改变位置 |
| `POST /tasks` | 创建有项目或无项目任务 | 状态、标题、可选描述与项目 ID；返回完整任务与版本 |
| `PATCH /tasks/{taskId}` | 编辑标题、描述或项目关联 | 变更字段、`expectedVersion`；项目关联可清除 |
| `POST /tasks/{taskId}/move` | 改变状态及排序 | `targetStatus`、`targetIndex`、`expectedVersion` |
| `POST /tasks/{taskId}/archive` | 归档任务 | `expectedVersion`；设置归档时间，不物理删除 |

控制器仅处理协议与输入校验；应用服务负责项目边界、任务规则和事务；数据访问层负责 PostgreSQL。前端通过 API 访问数据，不直接持有持久数据源。统一错误体至少包含稳定错误码与可读信息，不把数据库异常原文暴露给客户端。

## 实施方案

前端使用 React + TypeScript + Vite；后端使用 Java + Spring Boot；数据库使用 PostgreSQL。先以新的 Flyway 迁移把现有项目列模型转换为状态看板和可选项目关联，再实现项目、任务领域服务、HTTP API 与看板界面，最后接入拖拽并验证事务排序、冲突与持久化。开发环境提供可重复启动的 PostgreSQL 配置和应用启动说明；正式运行方式待部署场景明确后决定。状态排序的并发控制与筛选视图拖拽映射须在领域服务实现前确定。

后续接入 Agent 时，适配层调用同一应用服务或受控 API，提供列项目、读全局或项目筛选看板、创建、编辑、移动、归档等动作。MVP 不实现该适配层，也不允许 Agent 直接改表。对外开放前需确定 Agent 身份、读写权限、操作审计和重复请求处理方案。该边界属于[架构决策](../../../notes/proposed/architecture/2026-09-24-项目任务系统架构.md)，具体协议随 Agent 宿主确定。

## 依赖与风险

- 开发和集成验证依赖可运行的 Java、Node.js 与 PostgreSQL；版本及启动脚本在实施时根据可用环境确定。
- 单用户本地 MVP 不提供身份认证，服务应只监听本机地址；在认证、授权及审计完成前不得作为多人或公网服务部署。
- 状态内位置重排与跨状态移动需要同一事务；并发编辑要以版本冲突显式拒绝，不能依赖前端当前画面保证正确性。应在服务实现前确定状态级锁或等效串行化策略，防止并发移动造成位置重复或丢失。
- 现有 Flyway V1 以每个项目三列及必填项目关联建模；升级迁移必须考虑已执行 V1 的数据库及可能存在的数据，不能直接改写 V1。
- 多项目管理、项目重命名和任务归档仍纳入本计划。参考图中的四种状态先作为固定状态；若状态名、状态数量或其他卡片字段需要调整，应同步修改验收条件与任务来源。Agent 宿主和部署形态仍待确认，不影响本阶段独立交付。

## 验证策略与验收条件

- 使用真实 PostgreSQL 执行从 V1 升级及全新建库迁移，并运行后端集成测试：有项目和无项目任务均可创建；四种状态分组及项目筛选正确；状态内重排、跨状态移动及归档后位置正确且无重复；并发移动不丢失更新；异常操作回滚；过期版本返回 `409`。
- 通过 HTTP 客户端执行创建项目、创建任务、编辑、移动、归档的完整流程，检查状态码、JSON 字段、稳定 ID 与错误体；重启服务后数据仍可读取。
- 在浏览器完成创建项目、创建有项目和无项目任务、编辑项目关联、按项目筛选、拖拽排序与跨状态移动、归档任务；刷新后结果与服务端一致，并验证保存失败或版本冲突时的提示。
- 用至少一种浏览器外的普通 HTTP 客户端调用任务 API，证明后续 Agent 可接入的接口边界；这不等同于已完成 Agent 或 MCP 集成。
- 以上检查均需保存实际执行结果与环境信息；测试代码存在、计划已写或界面可打开均不单独构成验收通过。
